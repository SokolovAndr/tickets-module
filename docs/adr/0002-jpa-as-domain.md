# 2. JPA-сущности как доменные модели

## Status
Accepted

## Context
Проект — многомодульное Spring Boot приложение с бизнес-логикой
вокруг билетов, маршрутов и перевозчиков. Модули:
`api`, `impl`, `web`, `db`, `app`.

Классический подход в DDD-проектах — разделять три слоя моделей:
- Domain model (чистые POJO, не знают про JPA)
- Persistence entity (знает про JPA, маппится на таблицу)
- DTO (то, что уходит наружу через API)

Это даёт полную изоляцию домена от инфраструктуры, но требует
двух маппингов (domain ↔ entity, domain ↔ DTO) на каждый объект.
Для проекта из 4 сущностей это ~8 дополнительных мапперов.

Нужно решить: разделять модели по слоям или использовать одну
JPA-сущность на всех уровнях.

## Decision
Используем одну JPA-сущность одновременно как доменную модель
и как объект persistence. Разделение до DTO происходит только
на границе модуля `impl` → `api` через MapStruct-мапперы.

- `RouteEntity`, `TicketEntity`, `CarrierEntity`, `UserEntity` —
  и доменные модели, и persistence-модели.
- В `tickets-module-api` — только DTO, сгенерированные из OpenAPI.
- В `tickets-module-web` — два типа DTO, оба привязаны к web-слою:
  - **View-модели** (`MyTicketView`) — то, что уходит в Thymeleaf.
  - **Формы** (`RegistrationForm`) —
    то, что приходит от пользователя, с валидацией через
    Jakarta Validation (`@NotBlank`, `@Size`).

## Consequences

### Плюсы
- Меньше boilerplate — нет двойного маппинга domain ↔ entity.
- Меньше классов — 4 сущности вместо потенциальных 12+.
- Разработчик быстрее ориентируется в коде (один `TicketEntity`,
  а не три «тикета» в разных папках).
- Для проекта этого размера — адекватное решение.

### Минусы
- Домен **протекает** — сущность знает про `@Entity`, `@Table`,
  ленивые ассоциации. Тестировать доменную логику без JPA-контекста
  не получится.
- Если завтра потребуется сменить ORM (маловероятно) — придётся
  переписывать все сущности.
- Доменные инварианты смешиваются с аннотациями persistence —
  место для нарушения чистоты.

## Alternatives

### Разделять Domain / Entity / DTO
Отклонено: оверкилл для проекта из 4 сущностей. Даёт пользу при
большой доменной логике, но у нас основная логика — CRUD + пара бизнес-правил.
Соотношение «boilerplate / польза» не в пользу подхода.

### JOOQ вместо JPA
Отклонено: JOOQ даёт больше контроля над SQL, но требует держать
отдельные generated classes, что увеличивает связанность с БД.
Для 4 таблиц и простых запросов JPA — избыточно-достаточно.
Можно рассмотреть возможность комбинирования JOOQ + JPA, 
но в этом проекте не требуется такой уровень контроля на SQL.

## Notes
Пересмотреть решение, если:
- Появится сложная доменная логика — тогда разделение оправдано.
- Количество сущностей вырастет до 15+ — тогда boilerplate
  перестанет быть существенным на фоне общего объёма кода.
