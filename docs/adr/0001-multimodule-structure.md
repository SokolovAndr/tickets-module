# 1. Структура проекта (Maven-модули)

## Status
Accepted

## Context
Проект реализует систему продажи билетов: REST API, HTML-интерфейс,
работа с БД, генерация DTO из OpenAPI. Всё это можно собрать
в один Maven-модуль — так делает большинство пет-проектов.
Но с ростом кода монолит начнёт давать трения: слои перепутаются,
границы размоются, тесты станут запускаться долго.

Нужно решить: **один модуль** или **несколько**. Ключевое
требование: слои должны быть изолированы компилятором, а не
только соглашением.

## Decision
Используем **шесть Maven-модулей** с явными зависимостями.

| Модуль | Назначение | Java-код |
|---|---|---|
| `tickets-module-api` | Контракты REST API (DTO и интерфейсы, генерируются из OpenAPI) | ✅ |
| `tickets-module-impl` | Бизнес-логика, репозитории, JPA-сущности, UNIT-тесты | ✅ |
| `tickets-module-web` | Thymeleaf-шаблоны, MVC-контроллеры | ✅ |
| `tickets-module-db` | Только Liquibase-миграции | ❌ |
| `tickets-module-app` | Точка входа, интеграционные тесты, конфигурация | ✅ |
| `coverage-report` | Агрегация JaCoCo для SonarCloud | ❌ |

Граф зависимостей (стрелка = «зависит от»):
app → web → impl → api
app → db
app → coverage-report (только на этапе сборки)


Модуль `impl` **не знает** про `web` и `app`. Модуль `web`
**не знает** про `db`. Это проверяется компилятором Maven —
нарушение зависимостей не соберётся.

## Consequences

### Плюсы
- **Границы слоёв защищены компилятором.** Зависимости между
  модулями ограничены `pom.xml`: `api` не видит `impl`, `impl`
  не видит `web` и `app`, `web` не видит `db`. Нарушение этих
  правил ломает сборку. Дополнительно архитектурные правила
  зафиксированы в `ArchitectureTest` (ArchUnit).
- **Параллельная сборка** — Maven собирает модули без циклов,
  можно собирать только изменённый модуль (`-pl`, `-am`).
- **`db` без Java-кода** — миграции можно запустить независимо
  от приложения (в CI, в отдельном джобе, локально).
- **Понятный вход** — новый разработчик сразу видит, где что
  искать. Открывает `impl/routes/` — там вся логика по маршрутам.
- **Тесты разделены по смыслу** — unit-тесты в `impl`,
  интеграционные в `app`, не смешиваются.

### Минусы
- **Больше `pom.xml`** — 6 файлов вместо одного. Нужно
  поддерживать согласованность версий.
- **Дольше первая сборка** — `mvn clean install` собирает всё
  последовательно.
- **Небольшой оверхед для маленьких задач** — если нужно
  поправить одну строку в web, всё равно собирается вся цепочка
  (`impl → web → app`).
- **IDE индексация** — IntelliJ IDEA иногда «теряет» модули при
  переключении ветки. Лечится `Reload All Maven Projects`.
- **web → impl: размытая граница.** Web-контроллеры используют
    сервисы из `impl` напрямую. Это нормально, но создаёт
    связанность: web-слой знает про `AuthService`, `TicketsService`
    и т. д. Разорвать связь можно выделением `tickets-module-security`
    (см. комментарий в `ArchitectureTest`).

## Alternatives

### Один модуль (monolith)
Отклонено: границы слоёв держатся только на code review, что
рано или поздно нарушится. Для проекта с перспективой роста
это неприемлемо.

### Два модуля: `app` и `api`
Отклонено: слишком крупное разбиение. `api` действительно стоит
вынести (генерируется автоматически), но бизнес-логику, web и
БД держать вместе — значит потерять изоляцию persistence
от UI.

### Package-by-feature внутри одного модуля
Отклонено: то же, что монолит, но с более глубокой иерархией
пакетов. Даёт структуру, но не защиту границ.

### Gradle вместо Maven
Отклонено: не по теме решения (это ADR про модульность,
а не про инструмент сборки). Но как отдельная тема — Maven
выбран из-за более простой настройки CI и меньшего количества
сюрпризов с транзитивными зависимостями в multi-module build.

## Notes
Пересмотреть решение, если:
- Модуль `impl` разрастётся до 200+ классов — тогда его стоит
  разделить на `routes-impl`, `tickets-impl`, `users-impl`.
- **Известное архитектурное отклонение:** правило
    `web_should_not_depend_on_impl` в `ArchitectureTest`
    закомментировано. Причина — `RegistrationController`
    зависит от `AuthService` из `impl.oauth.service`. Разрыв
    связи требует выделения отдельного модуля безопасности —
    отложено до роста проекта. Полное обоснование — в Javadoc
    соответствующего `@ArchTest` в `ArchitectureTest.java`.
