# 5. Отклонение от правила web → impl

## Status
Accepted (as technical debt)

## Context
Модуль `tickets-module-web` зависит от `tickets-module-impl`:
контроллеры вызывают сервисы (`TicketsService`, `RoutesService`,
`AuthService`). Формально это нарушает принцип «UI не знает
про домен».

Правильный путь — выделить `tickets-module-security` с интерфейсом
`UserLookup`, чтобы `web` работал через абстракции. Но это
требует:
- нового Maven-модуля,
- переноса `AuthService`, `JwtService`, security-конфигураций,
- разрыва цикла `AuthService → UserRepository` через `UserLookup`,
- переписывания тестов.

## Decision
Оставляем прямую зависимость `web → impl` **осознанно**.
Правило `web_should_not_depend_on_impl` в `ArchitectureTest`
закомментировано с пояснением.

## Consequences

### Плюсы
- Не тратим время на рефакторинг ради архитектурной
  чистоты проекта из 4 сущностей.
- Меньше классов — не заводим интерфейсы-прокладки, которые
  ничего не абстрагируют.
- Ускоряется разработка: контроллер может напрямую вызвать
  сервис, не проходя через layer-indirection.

### Минусы
- Технический долг: при росте проекта `web` начнёт знать
  слишком много про внутренности `impl`.
- Сложнее изолированно тестировать web-слой — нельзя подменить
  impl на mock без поднятия контекста.
- Если завтра кто-то захочет заменить `impl` на другой модуль —
  придётся править все web-контроллеры.

## Alternatives

### Выделить `tickets-module-security`
Отклонено (пока): оверкилл для 4 сущностей и одного разработчика.
Вернуться к этому при росте.

## Notes
Пересмотреть решение, если:
- Появятся новые разработчики.
- Модуль `impl` разрастётся до 200+ классов.
- Возникнет потребность в изолированном тестировании web-слоя
  без поднятия impl.
