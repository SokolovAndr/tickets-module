# 3. Две цепочки Spring Security: сессии для UI и JWT для REST

## Status
Accepted

## Context
Приложение имеет два независимых способа доступа:
- **UI** (Thymeleaf, HTML-формы) — для обычного пользователя
  в браузере. Здесь важен stateful-опыт: cookie, redirect,
  сессия, работа с формами.
- **REST API** (`/api/**`) — для интеграций, мобильных клиентов
  и Swagger. Здесь stateful неудобен: клиенты не хранят
  cookies, каждый запрос автономен.

Классический вопрос: использовать **один** механизм для обоих
или **разделить**. Один механизм проще в поддержке, но создаёт
трения с обеих сторон: JWT в cookie для UI — небезопасно
(XSS читает localStorage, CSRF-проблемы), сессии для мобильных
клиентов — плохая переносимость (клиент должен таскать cookie jar).

## Decision
Используем **две независимые цепочки** Spring Security 6,
разделённые по URL-префиксу.

| Цепочка | Область                                            | Аутентификация | CurrentUserService |
|---|----------------------------------------------------|---|---|
| UI | `/login`, `/register`, `/routes/**`, `/tickets/**` | Form login + HTTP-сессия | `SessionCurrentUserService` |
| REST | `/api/**`                                          | JWT Bearer (OAuth2 Resource Server) | `JwtCurrentUserService` |

Обе цепочки имеют общий `UsersService` — источник истины
по пользователям. Резолвинг текущего пользователя абстрагирован
за интерфейсом `CurrentUserService`, чтобы бизнес-логика
не знала, откуда пришёл запрос.

## Consequences

### Плюсы
- **Правильная семантика каждого механизма:** UI получает
  stateful-опыт с CSRF-защитой и redirect-ами, REST — чистую
  stateless-модель, пригодную для мобильных клиентов.
- **Изоляция рисков:** XSS-уязвимость в UI не компрометирует
  REST API, и наоборот. Токены JWT живут в `Authorization`
  заголовке, cookies — в браузере, они не смешиваются.
- **Гибкость:** можно отключить один механизм, не задев другой
  (например, отключить UI, оставив только API).
- **Соответствие документации Spring:** это паттерн, описанный в официальных гайдах (Spring Security Reference, ...).

### Минусы
- **Две конфигурации для поддержки** — `WebSecurityConfiguration`
  и `ApiSecurityConfiguration`.
- **Два `CurrentUserService`** — `SessionCurrentUserService` для UI
  и `JwtCurrentUserService` для REST. Местами логика почти
  дублируется, но резолвинг из разных источников.
- **Тесты сложнее** — `@WithMockUser` работает по-разному
  в UI- и API-тестах.
- **Swagger UI** требует отдельной настройки в
  `SwaggerSecurityConfiguration`, чтобы работал на проде.

## Alternatives

### Один механизм — только JWT
Отклонено: неудобно для UI. JWT в cookie создаёт CSRF-проблемы,
JWT в localStorage — XSS-уязвимости. Redirect-ы после логина
и logout требует дополнительной обвязки. Для HTML-форм это
неестественный выбор.

### Один механизм — только сессии
Отклонено: неудобно для REST API. Мобильные и внешние клиенты
должны хранить cookie jar, что плохо сочетается с REST-семантикой.
К тому же сессии требуют централизованного хранилища при
горизонтальном масштабировании.

## Notes
Пересмотреть решение, если:
- UI станет SPA (React/Vue) — тогда сессии могут быть заменены
  на JWT или на гибрид с `httpOnly` cookie.
