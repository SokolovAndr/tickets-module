# 4. Кэширование списка билетов через Redis

## Status
Accepted

## Context
Endpoint GET /api/tickets/my вызывается при каждом открытии страницы
«Мои билеты». Данные меняются редко (только при покупке/возврате).
Под нагрузкой N запросов в минуту один и тот же userId повторяет
SQL-запрос к tickets + join с routes. На проде PostgreSQL — не
бесконечный, каждый запрос стоит ресурсов. Решение проектировалось под прод-нагрузку, 
но на Railway (Free) Redis не развёрнут, поэтому реально кэш включён только в профиле local.

Нужно: снизить нагрузку на БД и ускорить ответ для повторных запросов,
при этом не терять консистентность при покупке/возврате.

## Decision
Redis как распределённый кэш на уровне приложения через Spring Cache
(@Cacheable / @CacheEvict) используется только в профиле local. В профиле railway Redis не развёрнут,
поэтому Spring Cache отключён, и GET /api/tickets/my работает напрямую
с PostgreSQL.

- Ключ: `tickets:userTickets::<userId>`
- TTL: 30 минут
- Сериализация: JSON (GenericJackson2JsonRedisSerializer)
- Инвалидация: @CacheEvict при buyTicket и returnTicket
- Fallback: LoggingCacheErrorHandler — при падении Redis метод
  идёт в Postgres, ошибка логируется, но не роняет запрос

## Consequences

### Плюсы
- В local: response time для повторных запросов с ~80ms до ~5ms.
- В local: нагрузка на PostgreSQL снижается.
- В local: если Redis упадёт — приложение не сломается (fallback на Postgres).

### Минусы
- Дополнительная инфраструктура (Redis) — плюс к DevOps-сложности.
- Сериализация через JSON медленнее, чем binary (Kryo), но даёт
  читаемость в redis-cli — важно для отладки.

## Alternatives

### Caffeine (in-memory)
Отклонено для сценария распределённого кэша. Сейчас на Railway кэш
не используется, поэтому проблема неактуальна. Но если Redis появится
в production и приложение будет запускаться в нескольких репликах,
in-memory кэш даст рассинхронизацию между нодами. Redis выбран как
решение, которое сразу готово к multi-instance деплою.

### Hibernate Second-Level Cache
Отклонено: кэширует entity, а у нас DTO-ответ после маппинга.
Слишком низкоуровнево для задачи.

### Ничего не кэшировать, добавить индексы
Отклонено: индексы уже есть, проблема не в них, а в количестве
запросов на один и тот же ключ.

## Notes
Пересмотреть решение, если:
- Появится требование real-time консистентности (снизить TTL до 1 минуты).
- Redis начнёт падать чаще, чем раз в неделю (в профиле, где он включён — сейчас это local).
